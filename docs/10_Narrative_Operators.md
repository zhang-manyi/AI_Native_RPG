# 10. Narrative Operators

> 当前实现边界：村庄剧本按预定义事件、地点和条件执行，算子是叙事用途标签。以下生成式调度说明仅适用于旧版纯对话剧本；已禁用模型自由生成 `foreshadow`，模型不能决定新的事实、证物或回收条件。预定义伏笔及其 `payoff_target` 保留。开发者面板显示中文用途、触发原因和阻塞原因；本次未新增 AI 编剧层。


## 1. 职责

把叙事结构做成**离散的、可调度的算子**：确定性系统决定用哪个算子，LLM 只在算子给定的槽位里填内容。

解决的问题是自由生成的内容"局部合理、整体无形状"——每句都通顺，但没有铺垫和回收，没有逐步逼近核心的推进感。

> **算子已不再是调度单位。** 本文档描述的四个算子回答的是"这件事*怎么讲*"；决定"*发生什么*"的是事件层，见 [13_Narrative_Events.md](./13_Narrative_Events.md)。这是实现后修正的一处设计偏差：算子是修辞动作，没有前件和后件，因此拼不出情节——`foreshadow` 的触发条件退化成"账本没满且上一轮没埋"，沦为空回合的填充物。本文档其余部分（节奏规则、账本、张力与偏好的分离）全部仍然成立，只是作用在事件选定之后。

## 2. 三类算子

### 2.1 状态算子（确定性）

改变世界，不生成文本。一个算子 = **一组 Action Proposal**，因此走既有的 Validator，无需新权限机制。

算子由**事件声明用哪一个**，不再自己产生候选（[13 §2](./13_Narrative_Events.md#2-事件与算子是正交的两层)）。`relieve` 因此有了正确的含义：没有事件到条件的回合就是安静的，不必拿伏笔去填。

| 算子 | 作用 | 本场景中的形态 | 是否实现 |
|---|---|---|---|
| `foreshadow` | 埋下未来会回收的伏笔 | 写入 hidden fact + 登记进伏笔账本 | 是 |
| `reveal` | 让已可解锁的信息进入玩家视野 | 玛尔塔说出线索 | 是 |
| `escalate` | 提升某条线的紧迫度 | 洛伦察觉玩家在调查 | 是 |
| `reverse` | 不给新信息，改变已知信息的含义 | 见 §5 | 是 |
| `relieve` | 降张力，给玩家喘息 | 本轮不触发任何算子（隐式） | 隐式 |
| `complicate` | 让已解决的事重新出问题 | — | 否，单线场景无必要 |
| `converge` | 接上两条独立线索 | — | 否，只有一条主线 |

### 2.2 选择算子（确定性）

即 Experience Controller，两段式，见 §3。

### 2.3 生成算子（LLM）

在算子给定的槽位里填内容。算子提供的输入包括戏剧功能、参与者、以及**显式的禁止项**（如"不能揭露洛伦的身份"）。

## 3. 选择：张力准入 + 偏好排序

偏好和张力是两个正交维度，**分两段处理，不相乘**：

| 维度 | 含义 | 变化频率 | 用法 |
|---|---|---|---|
| 张力 | 现在该多紧 | 每个 beat 都在变 | 硬过滤（准入） |
| 偏好 | 玩家口味（探索/社交/阴谋） | 会话内基本不变 | 软打分（排序） |

相乘会导致"对味但不是时候"的候选仍然得高分——玩家偏好阴谋，刚连着三次揭露，第四个阴谋 beat 依然不该出。

代码见 [05_Narrative_Engine.md](./05_Narrative_Engine.md#22-experience-controller候选事件准入-排序确定性)。

### 3.1 节奏规则（张力准入的全部内容）

本场景只实现节奏约束，不做张力曲线拟合（一局 15-30 轮，曲线拟合无意义）：

- 不能连续两轮 `reveal`
- 不能连续 N 轮没有任何算子触发
- `escalate` 之后至少隔一轮才能再 `escalate`

判断依据是 `story_beats.recent_operators`。

### 3.2 张力的来源

本场景无战斗无数值，张力由三项构成：

| 来源 | 字段 |
|---|---|
| 逼近答案的程度 | `quests.<narrative.progress_quest>.stage` |
| 威胁 | `npc_a_threatened`（"说出去你儿子会是下一个"） |
| 不确定性 | 处于 `partial` 状态的 fact 数量 |

哪个 quest 承载第一项由剧本的 `narrative.progress_quest` 命名，不是框架里写死的 id（本场景是 `investigation`）。**这个通道必须有人推进，否则整条链是死的**：`rules.earned_stage()` 数已经说出口的 `paced_clues` 条数，Engine 每 tick 据此提一次 `advance_quest`，一次一步。曾经没有这个写入者，于是 stage 恒为 0——`escalate`（要 `stage >= 1`）一次不触发，张力停在 0.00，按 stage 写的伏笔回收条件永不到期。详见 [09](./09_Reference_Scenario.md)。

用"已说出口"而不是"可解锁"来计数：后者一个大方的回合就能满足，而前者是真发生过的 beat，且单调——没有东西能把一条已说出的线索收回去，所以 stage 不会倒退去反锁已经开放的内容。

一个未实现的低成本杠杆：`npc_b_aware_of_investigation`（洛伦是否知道玩家在调查）。一个布尔值即可把"走访证人"变成"被盯上了"。

## 4. 伏笔账本

`foreshadow` / `payoff` 必须成对。账本存在 `story_beats.open_foreshadowings`：

```
foreshadow → 写入 hidden Fact + 登记账本条目
                        ↓ (每个决策点检查)
     未回收的有哪些？到回收时机了吗？超期了吗？
                        ↓
payoff → 回收，从账本移除
```

每条账本条目记录：

| 字段 | 说明 |
|---|---|
| `fact_id` | 对应的 hidden fact |
| `planted_at_turn` | 埋下的轮次 |
| `payoff_condition` | 结构化条件（`{path, op, value}`），可被求值器判定 |
| `overdue_after_turns` | 超期阈值 |

`payoff_condition` 必须是结构化条件而非自由文本，否则账本无法自动判断"到时机了吗"。

可视化见 [07_Observability.md](./07_Observability.md#23-narrative-state-panel叙事状态面板)，指标见 [08_Evaluation.md](./08_Evaluation.md#21-叙事结构指标)。

## 5. 结构质量优先级

按坏掉之后的伤害排序。这个顺序决定实现和排查问题的先后。

| 优先级 | 项目 | 状态 | 说明 |
|---|---|---|---|
| 1 | 不自相矛盾 | 大部分由架构保证 | 事实源唯一 + NPC 只能说可见集合内的内容。度量见 [08 §2.1](./08_Evaluation.md#21-叙事结构指标) |
| 2 | 反转 | 触发条件已在剧本中 | `npc_a_threatened` 解锁后，玛尔塔此前的回避从"包庇"重读为"护子"。复用已有信息，不增加认知负担 |
| 3 | 伏笔回收 | 见 §4 | |
| 4 | 收束 | 待实现，条件已倒推 | 结局及其结构化成立条件见 [14 §4](./14_Case_Design.md#4-三个结局)。需要事件层先落地：现在没有任何状态表达"故事走到哪一步了" |
| 5 | 戏剧性反讽 | 不在本场景 | 需要 `visibility` 从"每 fact 一态"改为"每观察者一态" |

## 6. 与现有模块的对应

引入算子不新增模块：

| 模块 | 角色 |
|---|---|
| `check_triggers()` | 产出候选算子（带 `operator` 字段） |
| Experience Controller | 张力准入 + 偏好排序 |
| `generate_content()` | 在算子槽位里填内容 |
| Action Proposal / Validator | 算子效果的落地路径，不变 |
| `Fact` + `reveal_condition` | 伏笔账本的存储基础 |

## 7. 实现约定

- 实现 4 个算子（§2.1 表格），`relieve` 用"本轮不触发"隐式表达。
- 张力只做 §3.1 的节奏规则。
- 伏笔账本先做记录 + 超期告警 + 可视化；~~自动选择回收时机留作后续~~ —— **事件层之后这一条可做了**：伏笔挂到剧本的线索链上，回收目标由剧本指定，"该回收哪条"因此有了正确答案。原先做不了是因为账本条目与主线无关（[13 §9](./13_Narrative_Events.md#9-伏笔重新挂到线索链上)）。
- `StoryBeats` schema 见 [04 §4.1](./04_World_State_Manager.md#41-storybeats)。
- 生成算子的 prompt 经 [11_Prompt_Lab.md](./11_Prompt_Lab.md) 选定。

### 7.1 实现时的四条解读

设计文档没写到、实现时必须定下来的：

**`payoff` 不是第五个算子**，是 `reveal` 的完成态：候选带 `pays_off=fact_id` 时，执行阶段一并提交 `reveal_fact` 与 `pay_off_foreshadowing`。这样算子表保持 §2.1 的「4 个 + 隐式 relieve」，不必为回收单开一类。

**`reveal` 算子不负责解锁，只负责「说出口」。** `PlayerView` 已经在 `reveal_condition` 满足的那一刻自动放开可见性，不需要任何 action——所以算子能调度的不是披露，而是*讲述*：条件已满足、但存储的 `visibility` 仍是 `hidden` 的 fact，正是「玩家有资格知道，但还没人说出来」。这个差值是确定性的，因此可调度；也因此 Engine 永远无法靠算子拓宽可见性（[04 §3.3](./04_World_State_Manager.md#33-叙事推进不等于披露授权)）。

**§3.1 第二条规则不是准入过滤器。** 「不能连续 N 轮没有任何算子触发」与另两条方向相反：那两条否决候选，这条要求出现候选，做成硬过滤会把自己过滤空。实现为**饥饿保护**——连续 N 轮 `relieve` 后放松那两条冷却，判断依据是「故事停摆比稍微赶一点更糟」。

**张力上限必须随进度抬升。** 见 [09 §4](./09_Reference_Scenario.md#4-建议的实现顺序对应依赖关系) 末尾：常量阈值会让张力永久停在略高于阈值处，把所有以更高张力为条件的内容变成死内容。
