# 13. Narrative Events

## 1. 为什么要有这一层

[05 §1](./05_Narrative_Engine.md#1-职责划分) 把 Narrative Engine 比作 RimWorld 的 AI Director，[05 §2.1](./05_Narrative_Engine.md#21-规则触发确定性) 的示例里候选是 `event_type="betrayal"`、`event_type="npc_turns_hostile"`——**是事件，不是算子**。实现时粒度换成了算子（`foreshadow` / `reveal` / `escalate` / `reverse`），`EventCandidate.operator` 这个字段是那时加的（[05 §5](./05_Narrative_Engine.md#5-数据结构) 变更表第一行有记录），而事件那一层没有落地。

代价在一轮真实对局里显形了（症状记录见 [09 §4](./09_Reference_Scenario.md)）：

**算子是修辞动作，不是情节。** "埋一个细节 / 说一条线索 / 加压 / 让旧信息变味"都是*怎么讲*，没有前件和后件。没有前后件就拼不出情节，于是"这回合该发生什么"这个问题没有依据可答。`_foreshadow_candidates` 的触发条件因此只剩下"账本没满且上一轮没埋"——**没有任何一条问"这个故事现在需要一条伏笔吗"**。

**于是 `foreshadow` 沦为空回合的填充物。** 它的 `intensity=0.3` 是五个候选里最低的（payoff 0.7 / reverse 0.8 / escalate 0.6 / reveal 0.5），所以只要有别的候选它就必然落选——它实际上只在"其他什么都没有"的回合里被选中，填的正是本该 `relieve` 的那些回合。而 [05](./05_Narrative_Engine.md) 开头明确写着「返回 `None` 是正常结果，不是失败；生成叙事最常见的出错方式就是坚持每回合都得有事发生」。架构专门为"这回合什么都不发生"留了位置，实现却把那个位置占了。

**伏笔因此既无目标也无理由。** `payoff_condition` 由模型自己写，所以它同时决定"埋什么"和"什么时候算收"，"回收"只是账本划掉一行，跟主线没有因果关系。实测三次分别埋了窗上的绳子、一枚纽扣、半枚白蜡——内容漂移是因为**没有地方可通**：生成 prompt 只给可见 facts（[10 §2.3](./10_Narrative_Operators.md) 的立场，与 `tools.py` 一致：没进 prompt 的文本不可能从 prompt 泄漏），所以模型被要求"埋一个以后会变成线索的细节"，却看不见任何一条真线索。这个任务在信息上无解。

**结论**：加一层事件，算子保留但降级。

## 2. 事件与算子是正交的两层

| 层 | 回答 | 例子 |
|---|---|---|
| 事件 | 发生了**什么** | 洛伦来敲玛尔塔的门；村里开始有人躲着你 |
| 算子 | 这件事**怎么讲** | 先埋一笔（`foreshadow`）／让人说出口（`reveal`）／让旧信息变味（`reverse`） |

事件有前件（触发条件）、后件（数值与状态变化）、分支（一个事件可以有多个结果）。算子没有这三样，所以算子不能充当调度单位。

**新的调度链**：

```
可触发的事件（剧本 + 世界状态）      ← 取代 check_triggers 的算子候选
        ↓  张力准入 + 偏好排序        ← Experience Controller，不变
    选中一个事件（或 None）
        ↓  事件声明用哪个算子表达
    算子 + 事件内容 → 生成 prompt     ← 模型拿到的是"这件事 + 这个修辞方式"
        ↓
  Action Proposal → Validator        ← 不变
```

已有的机制全部保留，而且变得更有意义：

- **节奏规则**（不能连续两轮 `reveal`、饥饿保护）仍作用在算子上，但现在约束的是真实情节的呈现节奏，而不是填充物的节奏。
- **两段式选择**（张力准入 + 偏好排序）原封不动——它本来就是为"候选事件"写的，见 [05 §2.2](./05_Narrative_Engine.md#22-experience-controller候选事件准入-排序确定性) 的函数签名。
- **伏笔账本**仍是账本，但记的是"事件 A 埋下的东西由事件 B（或某条线索的揭露）回收"，这才是真的债。
- **`relieve` 终于能正常发生**：没有事件到条件，这回合就安静，不必拿伏笔去填。

### 2.1 算子候选全部收进事件

没有事件到条件时，**不允许**退化出一个算子级的小 beat。理由是那正是本文档要修的东西——填充物无论规模大小都是填充物，而"没有事件就安静"恰好是 [05](./05_Narrative_Engine.md) 那句"返回 None 是正常结果"的正确形态。

代价是剧本必须写全：没有事件覆盖到的世界状态，就真的什么都不发生。这是明确接受的代价，不是疏漏。

## 3. 事件内部：什么定死，什么留给模型

**定死**（否则系统失去核心性质）：

| 项 | 形式 | 为什么不能交给模型 |
|---|---|---|
| 触发条件 | 结构化 `Condition` | 已有求值器；自由文本无法判定 |
| 结果集 | 每个结果的数值/状态变化写死 | 结果会改变解锁，见下 |
| 哪个结果发生 | 由玩家选择或世界状态决定 | 同上 |

最后两条是 [04 §3.3](./04_World_State_Manager.md#33-叙事推进不等于披露授权) 的直接推论：**没有任何 actor 可以绕过 `reveal_condition`**。如果模型能决定事件结果，它就能间接决定解锁什么，那条约束就破了。

**留给模型**：

- 这个事件在此刻、以这个 NPC 的口吻、在玩家已知这些事的前提下，**怎么被讲出来**；
- **玩家的自由文本回应算作哪个结果**——这一步是分类，不是决策。

第二条是关键：**选项不必是按钮**。[03 §5](./03_Player_Model.md#5-当前实现范围) 已经说过固定选项会把 Agent 降级成状态机查表。事件定义"有哪几个结果"，玩家自由说话，模型把话映射到某个结果——结构是确定的，交互是开放的。映射复用 NPC 那次已有的调用顺带输出（[03 §5](./03_Player_Model.md#5-当前实现范围) 对 `player_intent_tag` 用的就是这个手法），不额外增加请求。

### 3.1 每个事件都有默认结果和句数上限

一个事件不能永远不结束。但**上限不该表现为"NPC 主动推进度"**：那等于让 NPC 决定事件结果，而结果会改数值和状态——又一次绕过 §3 的约束。而且玩家会察觉到，聊到第 5 句她忽然主动交底，原因是计数器到了。

所以每个事件声明一个**默认结果**：到了句数上限仍没有任何结果被触发，就落默认结果，事件关闭，Director 去选下一个。默认结果通常是"这次没谈成"——数值小幅变化甚至不变。

这样上限是确定性的，模型仍然只管台词。而且"这次没谈成"本身是有意义的剧情状态而非失败：今晚没松口，明天再来，或者去别处找线索——正好通向 §4 的时间制与多地点。

句数上限**写在剧本里**（一次寒暄和一次交底该有不同的耐心），给一个全局默认。开发期取小值（3-4 句）足够看出机制是否工作，正式值 6-8。

### 3.2 事件需要"进行中"这个状态

现在世界里没有它：每个回合独立，`pending_event` 传一句 hook 就没了。事件层要成立，`StoryBeats` 上需要 `active_event`（哪个事件在进行、进行到第几句）。这是新设计里必须有、当前完全没有的东西，清单见 §7。

## 4. 时间制

### 4.1 三个时段 + 收束段

**一天三个时段（上午/下午/晚上），每个时段只能去一个地点。**

这给了系统现在完全没有的东西：**成本**。现在玩家的每个动作都免费，问不出来就再问一句，所以"进展慢"感觉像卡住而不像压力。有了时段，每个选择都在排除别的选择——从这一刻起玩家才真的在做决定。这也是 Player Model 能区分玩家风格的前提：`PlayerProfile` 至今没有写入方，部分原因是玩家没有可区分的行为。

**天数上限**到了就收束。它同时给"被洛伦先动手"这个结局一个自然的时钟——否则洛伦为什么现在动手需要一个额外解释。`time_day` 字段已存在（`world.yaml` 有 `time_day: 1`），只是从不推进：这不是加字段，是让已有字段动起来。

本文档原先写"建议 3-5 天"，[15 §6.2](./15_Event_Script.md#62-三条结局路径) 的验算把它定到了 **4**，理由在那里（真相路径需要 9 个时段，3 天只有 9 个、零缓冲）。数字本身住在剧本里（`world.yaml` 的 `story_beats.day_limit`）而不是代码里，因为它是*这个案件*的长度：见 [15 §6](./15_Event_Script.md#6-时段预算验算)。

**每天三个时段用完后有一个收束段**：整理线索 + 塔罗占卜。它**不占用时段**，是自动到来的过场。

考虑过"晚上默认在家整理"并否决了，两个理由：

- **夜晚是这个故事最该有压力的时段**（失踪发生在雨夜，玛尔塔夜里不敢开门，洛伦晚上在森林附近活动）。把夜晚固定成安全的整理时间，等于把最有张力的时段变成最安全的时段。
- 它会削弱刚建立的成本感：如果第三个时段总是自动的，实际上每天只有两个选择，玩家会算出这一点。

拆开之后，"夜里出门"成为可选且有代价的大胆行为——第三个时段去森林是主动冒险，正好通向"被洛伦先动手"。**风险与选择挂钩，而不是被时间表安排掉。**

### 4.2 整理线索与塔罗

**整理线索只重述已知，不产生新信息。** 否则它就是一条免费的推进通道，时段成本白设。它把散落的 fact 组织成"我现在知道什么、还缺什么"——输入正是 `PlayerView` 的可见集合，因此天然安全：它读不到任何 hidden fact。

**塔罗占卜给暗示性但不确定的提示。** 占卜这个形式天生允许模糊，所以它可以读世界状态（还有几条线索未揭露、张力多高）然后输出抽象意象，既不泄漏具体 fact 又真的有信息量。这是少见的"能用 LLM 且不违反 visibility 约束"的位置。一天一次的频率让它保持仪式感。

### 4.3 NPC routine：不做

考虑过让 NPC 有日程（去了某处找不到人），否决了。原因不是实现难（`NPCWorldState.location` 已在），是**它和时间制叠加会产生挫败感而非策略深度**：玩家花掉一个时段发现人不在，而他没有信息去预判谁在哪——那不是决策，是抽奖。要让它成为决策，得先设计一套让玩家学到 routine 的机制，那是一整层新东西。

而 routine 想要的效果（时段的选择有代价）时间制本身已经给了。加 routine 只是把代价从"不能同时去两个地方"变成"可能白跑一趟"，边际收益很小。

需要"人不在"这种情节时，用**事件**表达：某个特定时段洛伦不在森林，因为他去了玛尔塔家门口——那本身是剧情。**有意义的一次缺席，不是每天随机的日程。**

## 5. 声音层次

加入旁白和第三个 NPC 后，"谁在什么时候说话"必须定下来。做法是**固定层次，不是角色抢麦**：一个回合里声音按固定顺序出现，每层可以缺席。

| 顺序 | 声音 | 内容来源 | 何时出现 |
|---|---|---|---|
| 1 | 旁白（感知型） | 世界，**必须过可见集合** | 进入新地点、场景有变化时；不是每回合 |
| 2 | NPC 台词 | 该 NPC 的记忆与 persona | 被搭话的那一个 |
| 3 | 旁白（反应型） | **已知信息之间的关系**，不引入新信息 | 有依据时：信息冲突、低置信陈述 |

固定顺序**可预测**，玩家读得懂；而每层的信息来源与约束不同，分开也便于保证旁白不越界。

### 5.1 旁白只能读可见集合

**这必须是机制而非嘱咐。** `build_scene` 已经确立了模式：类型签名只接受 `VisibleState`，从不导入 `WorldState`，还有测试钉住那个 import 的缺席（[07 §2.4](./07_Observability.md)、[12 §7](./12_Web_Interface.md)）。旁白走同一条路。

旁白比 NPC 更危险，理由有两条：它是"客观"声音，玩家会信它——**NPC 说漏嘴是剧情，旁白说漏嘴是 bug**；而且它的诱惑更大，"提示玩家该往哪走"很容易滑成"告诉玩家答案"。

**反应型旁白特别有价值**：它是唯一能提示不确定性而不泄漏内容的方式。"真的是这样吗"不告诉玩家答案，只标记这里有值得怀疑的东西。而且它可以确定性触发——玩家刚听到的话与已知 fact 冲突、或那句话基于一条低置信记忆时才出现。**有依据的反应，不是随机的气氛。**

### 5.2 同场景只有一个对话对象

同一时刻只有一个 NPC 是对话对象。让两个 NPC 互相说话需要 NPC 之间的关系、各自对第三方在场的反应、以及谁听到了什么——最后一项直接踩到 [10 §5](./10_Narrative_Operators.md#5-结构质量优先级) 那条"戏剧性反讽需要 `visibility` 从每 fact 一态改为每观察者一态"，而那条明确不在本场景范围。

需要"洛伦出现在酒馆、玛尔塔不敢说话"这种场面时，用**事件**表达：那是剧本写好的一个特定场面，不是通用的多人对话机制。

## 6. 不可靠的 NPC 怎么不被当成 bug

引入会说错话的 NPC 有一项必付成本：**"NPC 说错"和"系统出 bug"在玩家眼里长得一样**。不解决的话第三个 NPC 就是净负担。

而且这件事**不能只靠 prompt**。让模型"说错时带上'可能'"，前提是它知道自己在说错——但它拿到的是记忆里的一条内容，那条内容对它就是真的。它没有"这是错的"这个视角。

所以从**数据层**给：记忆条目带置信度，低置信度的记忆进 prompt 时标注成"你不太确定这件事"，模型据此选择语气。`SemanticMemory` 已有 `confidence`；`EpisodicMemory` 有 `importance` 但没有置信度，需要补（清单见 §7）。这样"可能……"不是修辞装饰，而是**世界状态的忠实表达**。

**更强的形式：让 NPC 给出"要么 A 要么 B"。** 这把不确定性变成玩家的工作而不是系统的噪音——玩家得去验证哪个是真的，而验证本身就是调查行为。机制上是一条 fact 带两个候选值，验证条件满足后收敛到一个。

## 7. 需要新增的可读状态

本文档要求的新状态，集中在这里。每一项都必须是合法的 `Condition` 路径，否则剧本写不出对应的触发条件。

| 状态 | 用途 | 现状 |
|---|---|---|
| `active_event`（事件 id + 已进行句数） | §3.2 事件的进行中状态 | 完全没有 |
| 时段（`time_slot`）与天数推进 | §4 时间制 | `time_day` 存在但从不推进；时段没有 |
| 访问过的地点集合 | "首次到达 X"作为触发条件 | `player_locations` 只有当前位置，没有历史 |
| 用过的伏笔提示（hint id） | 防止同一线索的同一角度被埋两次 | 没有；与 `spent_one_shots` 同类 |
| 承诺（玩家答应过什么） | 支线改变主线形状，见 §8 | 没有 |
| `EpisodicMemory.confidence` | §6 语气标记不确定性 | 没有（只有 `importance`） |

`Condition` 目前能读 `relationships.*` / `quests.*` / `story_beats.*`（生成的 payoff 条件白名单是 `FORESHADOW_PAYOFF_PATH_PREFIXES`）。以上多数可以挂在 `story_beats` 下，避免新开顶层字段。

**道具系统不做。** 想要的效果（拿到某个东西从而能推进）用现有 `Fact` 就能表达：一条 `revealed` 的 fact 就是"玩家掌握了这个东西"。道具需要物品栏、获得/使用/失去、以及"持有某物"作为条件路径，是一整个新的状态类别；等真的需要"用某物在某处"这类交互时再加。理由与 §4.3 同类：范围失控的典型入口。

## 8. 支线的作用是改变主线的形状

条件没达到时不应该卡住，而应该掉到支线，支线改变数值，数值再喂回主线。这修掉"进展慢"的根本原因：现在条件不满足就什么都不发生（实测一局出现 7 个 `relieve`），玩家没有可做的事去改变条件。

但有个陷阱：**如果支线只是"涨信任然后回主线"，它就是换皮的进度条**，玩家会感觉到。要有意义，支线得改变主线的*形状*而不只是*进度*——例如为了让玛尔塔开口而答应替她保守某件事，这个承诺后面会限制你能做什么（这是 §7 里"承诺"状态的用途）；或者你去问了别人，玛尔塔知道后信任反而降了，但你从另一条路拿到了信息。

这也接上"结局差别大、由玩家选择自然达成"：**差别大的结局不是靠结局本身写得不同，是靠中途积累的状态不同。** 所以事件的后件（数值/状态变化）比事件的文本重要得多。

## 9. 伏笔重新挂到线索链上

§1 说明了乱埋的机制原因：`payoff_condition` 由模型自己写，所以埋的东西通向不了任何地方。新设计里反过来——

**`foreshadow` 不再是"编一个细节"，而是"把剧本里某条线索的第 N 个提示角度讲出来"。** 剧本给每条线索挂若干 hint（例如 `clue_2_identity` 下挂"走路的样子"、"靴底的泥"、"那件外衣"），于是：

| 问题 | 新答案 |
|---|---|
| 埋什么 | 剧本给定，必然与案件有关 |
| 什么时候收 | 那条线索被揭露时自动回收 |
| 会不会重复 | 已埋过的角度、已揭露的线索都在世界状态里查得到 |

三个角度指向同一个结论，正是 `MAX_OPEN_FORESHADOWINGS = 3` 背后 Three Clue Rule 要的东西（该常量的注释已经引了这条）。

**这同时让 [10 §7](./10_Narrative_Operators.md#7-实现约定) 那条「自动选择回收时机留作后续」变成可做的**：现在做不了，是因为账本里的条目与主线无关，"该回收哪条"没有正确答案。

已防住的一类重复：`_reveal_candidates` 会跳过 `visibility` 已是 `REVEALED` 的 fact。**需要新防的**是同一条线索的同一个 hint 被埋两次——即 §7 里的"用过的伏笔提示"。

## 10. 已知边界

明确不做，与 [09 §3](./09_Reference_Scenario.md) 表格里"不在本场景范围"的那些同性质：

| 项 | 理由 |
|---|---|
| NPC routine | §4.3：与时间制叠加产生抽奖而非决策 |
| 道具系统 | §7：一整个新状态类别，`Fact` 已能表达所需效果 |
| 多 NPC 同场景对话 | §5.2：需要"每观察者一态"的 visibility，[10 §5](./10_Narrative_Operators.md#5-结构质量优先级) 已列为不在本场景 |
| 玩家自由移动之外的世界互动（搜查、使用物品） | 需要一整套玩家动作类型；本文档只加"移动"与"结束对话" |

## 11. 每个结局必须可达

这是已经踩过两次的坑，值得写成约定：

- `quests.investigation.stage` 有作者、有读者、没有写入者 → 三条伏笔永不到期、张力恒为 0；
- `killer_identity` 写了两个通道，"独立调查"那条因为玩家不能移动而是死的。

同一个失败模式：**作者写了一条路，没有人验证它走得通。** 剧本加载器校验 `path` 能否解析，不校验值能否达到。

所以事件设计的产物里，**每个结局都要附一条具体的状态路径**：从初始状态出发，经过哪些事件、每步改哪个数值、最后满足哪个条件。写成这样之后，加载器可以校验"每个结局至少有一条可达路径"，把这类静默内容 bug 挡在启动时。内容部分见 [14_Case_Design.md](./14_Case_Design.md)。

## 12. 玩家动作

事件层需要玩家能主动做两件事，而现在玩家唯一能做的是说话——所有进展都得从 NPC 嘴里出来，这是"进展慢"的结构原因之一。

| 动作 | 说明 |
|---|---|
| 移动到某地点 | 消耗一个时段；`ActionType.MOVE` 已存在但 `_apply_move` 写的是 `npcs[actor_id].location`，玩家不在 `npcs` 里，所以这条路径**从未存在** |
| 结束当前对话 | 关闭 `active_event`，落到默认结果（§3.1） |

玩家动作**同样走 Action Proposal → Validator**，不新开写入路径。这是 [04](./04_World_State_Manager.md) 单一写入路径的直接要求，也意味着需要一条"玩家只能移动到相邻地点"的规则（`_move_must_be_adjacent` 已有，但它读的是 NPC 的位置）。

对应的 API 面变化见 [12_Web_Interface.md](./12_Web_Interface.md)：现在只有 `POST /turn`（说一句话），没有"做一件事"的入口。
